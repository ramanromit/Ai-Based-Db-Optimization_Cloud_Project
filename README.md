# CAQI — Criticality-Aware Autonomous Query Intelligence

**An SLA-aware, reinforcement learning-based framework for intelligent database resource allocation in cloud-based payment systems.**

CAQI prioritizes payment database workloads according to business criticality, applies constrained reinforcement learning to optimize resource allocation, and incorporates a security-aware layer to distinguish legitimate requests from suspicious activity.

## Overview

Online payment systems must process authorization-critical database operations within strict latency budgets while simultaneously handling settlement, reconciliation, and analytical workloads.

Conventional shared-resource allocation and aggregate auto-scaling may not adequately protect critical authorization queries from traffic bursts generated by lower-priority workloads.

CAQI addresses this challenge through a combination of:

- Business-criticality-aware query classification.
- Proximal Policy Optimization (PPO) for autonomous resource allocation.
- Lagrangian penalties for SLA-aware optimization.
- Request-legitimacy and behavioural risk assessment.
- Asynchronous decision explanation and audit logging.
- Safety-gated evaluation and promotion of candidate policies.

The project is evaluated in a simulated workload environment and uses a cloud-oriented AWS architecture.

## Key Features

### 1. Criticality-Aware Workload Classification

CAQI classifies database operations into three priority tiers based on the identity of the calling service and the configured workload classification rules.

| Priority | Workload class | Example operations | Configured latency target |
|---|---|---|---:|
| P0 | `AUTH_CRITICAL` | Balance checks, idempotency lookups, fraud-checkpoint reads | 10 ms |
| P1 | `SETTLEMENT_CRITICAL` | Settlement, reconciliation, ledger operations | 150 ms |
| P2 | `ANALYTICAL` | Reporting, merchant summaries, analytical queries | 1,000 ms |

These are project-configured targets, not universal database performance guarantees.

### 2. Reinforcement Learning-Based Resource Allocation

CAQI models resource allocation as a Constrained Markov Decision Process (CMDP).

The optimization component uses:

- **PPO:** Proximal Policy Optimization for learning resource-allocation decisions.
- **Gymnasium:** Simulation environment for workload and resource-management interactions.
- **Stable-Baselines3:** PPO implementation.
- **PyTorch:** Neural network and policy learning.
- **Lagrangian penalty:** Incorporates the cost of violating the configured authorization-latency constraint.

The policy observes the simulated system state, selects an available resource-management action, and receives feedback based on performance and constraint violations.

### 3. Comparative Evaluation

CAQI evaluates three resource-allocation approaches:

1. Baseline — criticality-agnostic resource allocation.
2. Unconstrained PPO — reinforcement learning without the explicit SLA constraint.
3. Constrained CAQI — PPO-based optimization with an SLA penalty.

Evaluation metrics include:

- Authorization P99 latency.
- Throughput.
- SLA compliance.
- Resource utilization and cost, where measured by the implementation.

### 4. Security-Aware Request Handling

The security extension separates **request criticality from request legitimacy**. A high-priority request is not automatically considered trustworthy.

Depending on the enabled implementation, security checks include:

- HMAC-SHA256 verification of signed service-identity claims.
- Request-velocity and behavioural anomaly detection.
- Idempotency-key and modified-payload replay checks.
- Financial transaction risk heuristics.
- Risk scoring and threat classification.
- Quarantine, throttling, temporary blocking, and analyst escalation.

Suspicious requests can be diverted to a verification path instead of receiving protected authorization capacity.

HMAC-SHA256 provides integrity and authenticity verification for signed data; it does not encrypt the payload or independently establish that a transaction is legitimate.

### 5. False-Quarantine Rate (FQR)

The security-aware design includes a False-Quarantine Rate constraint to measure how frequently legitimate requests are incorrectly quarantined under the project's evaluation definition.

FQR helps assess the trade-off between containing suspicious traffic and avoiding unnecessary disruption to legitimate payment operations.

### 6. Auditing and Safe Policy Adaptation

The architecture supports:

- Asynchronous decision explanations and audit records.
- Candidate-policy evaluation against the current policy.
- Safety-gated policy promotion.
- Cloud monitoring and workload evaluation.

These capabilities are subject to the functionality enabled in the current deployment.

## Datasets and Workloads

CAQI distinguishes database workload generation from financial fraud-risk analysis.

| Data source | Purpose |
|---|---|
| Synthetic TPC-style payment workload | Generates simulated P0, P1, and P2 query workloads for resource-allocation experiments. |
| PaySim | Supports financial transaction fraud-risk analysis when integrated into the security pipeline. |
| IEEE-CIS Fraud Detection | Can provide transaction and identity-related features for fraud analysis if integrated. |

**Note:** TPC-style refers to a workload inspired by transaction-processing benchmark concepts; it does not imply that CAQI runs an official TPC benchmark. PaySim and IEEE-CIS should only be described as active training or evaluation datasets if the implementation actually uses them.

## Evaluation Results

In the reported demonstration, CAQI produced the following authorization P99 latency observations:

| Approach | Authorization P99 latency |
|---|---:|
| Criticality-agnostic baseline | 148.76 ms |
| Constrained CAQI | 4.40 ms |
| Configured P0 latency budget | 10 ms |

The observed CAQI P99 was below the configured budget in this demonstration.

The unconstrained-PPO result and numerical security-detector metrics were not available in the supplied evaluation material and are therefore not reported here.

These results are specific to the tested environment and workload. They do not constitute a formal latency guarantee or establish performance under every production condition.


## Getting Started

### Prerequisites

Install the tools required by the components you intend to run:

- Python 3.10 or a compatible version supported by the project's dependencies.
- Node.js and npm.
- Git.
- Docker, if using containerized local services.
- Terraform and AWS CLI, if deploying the cloud infrastructure.

### 1. Clone the Repository

```bash
git clone <YOUR_REPOSITORY_URL>
cd CAQI
```

Replace `<YOUR_REPOSITORY_URL>` with your GitHub repository URL.

### 2. Set Up the Python Environment

```bash
python -m venv .venv
```

Activate it on Windows:

```bash
.venv\Scripts\activate
```

Activate it on Linux or macOS:

```bash
source .venv/bin/activate
```

Install the dependencies using the actual dependency file in the repository:

```bash
pip install -r backend/requirements.txt
```

If the backend and reinforcement-learning components have separate dependency files, install each as documented in the repository.

### 3. Configure Environment Variables

Create a local `.env` file based on `.env.example`, if provided.

Configure the required database connection, application settings, and security secrets. Never commit real credentials, AWS access keys, HMAC secrets, or private dataset files to GitHub.

### 4. Start the Backend

For a FastAPI application whose entry point is `main.py`:

```bash
uvicorn main:app --reload
```

Run this command from the directory containing the applicable `main.py`, or adjust the module path to match the actual project.

### 5. Start the Frontend

```bash
cd frontend
npm install
npm run dev
```

Open the local development URL printed by Vite.

## Security Considerations

- Store secrets outside source control.
- Verify signed identity claims using a well-defined canonical representation.
- Implement replay protection and atomic idempotency handling.
- Keep suspicious requests isolated from protected authorization capacity.
- Exclude untrusted or quarantined data from policy retraining unless it has passed appropriate validation.
- Validate candidate policies before deployment.
- Avoid exposing sensitive payment information in logs or dashboards.

## Limitations

- Results from a simulated workload may not directly generalize to production payment systems.
- Latency measurements depend on the environment, workload distribution, database configuration, and resource availability.
- Security performance must be established through measured precision, recall, false-positive, and false-quarantine metrics.
- Cloud deployment and optional integrations depend on the features actually configured and tested.
